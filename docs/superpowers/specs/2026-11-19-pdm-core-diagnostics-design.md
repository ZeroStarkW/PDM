# PdM 核心诊断闭环设计

## 意图

让维护人员可以按设备类型维护诊断规则，由实时遥测触发规则，并把诊断因素、依据和建议保存在告警和维修工单中。系统继续提供现有资产、基线、数据质量状态、告警与工单能力，补齐维修结果反馈。

## 目标

- 用户可创建和维护设备类型，并将设备分配到类型。
- 用户可为设备类型维护启用/停用的诊断规则：转频阶次、可用测量指标、比较方式、阈值、优先级、主导因素、建议。
- 新规则参与实时诊断，告警中心展示因素、触发依据和建议。
- 规则编辑不改写已发生告警的诊断快照；规则匹配确定、可追溯。并发编辑使用期望版本拒绝过期表单；按阶次命中的历史告警保存实测峰频和目标峰频。
- 工单闭环记录现场发现和采取措施，用于后续评估诊断质量。
- 继续呈现设备在线/传感器质量、基线学习和健康状态，避免把坏数据打成故障。

## 非目标

- 本轮不实现剩余寿命预测、机器学习模型训练、自动备件采购、外部 EAM/MES 集成或完整的规则表达式语言。
- 不改变现有健康指数和严重度公式；可配置规则负责解释主导因素。
- 不承诺仅凭额定转速对可变速设备任意高阶频率作精确分析。

## 约束与现状

- 后端为 Spring Boot/JPA/PostgreSQL；时序数据由现有 InfluxDB 存储管理。
- 前端为 Vue 3/TypeScript。
- 当前设备没有设备类型；健康指数计算器将因素判断写死为固定字符串。
- 遥测提供 1X/2X 振幅、速度 RMS、加速度峰值/峭度、包络 RMS、温度及可选 topPeaks。
- 告警已有主导因素字段，维修工单已有处理备注；仪表盘已有传感器质量/离线计数。
- 工作区已有用户未提交改动；实现必须保留并集成这些改动，不得回滚或覆盖无关文件。

## 方案

考虑了两种设备分类方式：预置设备类型便于开箱使用但新增类别要修改程序；用户维护类型目录灵活，需防止删除仍被设备引用的类型。采用用户维护类型目录，按编码唯一、名称可编辑；系统提供 GENERAL 通用类型，旧设备和新建设备默认归入 GENERAL。

规则采用受控字段而非用户输入脚本：指标限定为现有遥测中的 1X、2X 振幅/相对基线比、1X/2X 和 2X/1X 比、速度 RMS、加速度峰值/峭度、包络 RMS、温度，以及按额定转速估算的谐波峰幅值/SNR；比较符限定为大于/大于等于/小于/小于等于。规则只含一个判断条件。按优先级从高到低评估，首条匹配规则成为主导因素。无规则命中时使用明确的通用复测提示，不再返回硬编码的特定故障解释。

对比自由表达式规则引擎，此方案只能覆盖现有数据和简单阈值，但输入可校验、行为可解释且更适合当前 MVP。阶次超出 1X/2X 的匹配限于遥测峰值与额定转速估算频率的容差窗口，页面明确标出可变速设备的精度限制。

告警/工单持久化因素名称、规则说明、建议和触发值快照，以免规则后续修改造成历史语义变化。诊断规则不改变健康指数；阈值告警仍由现有 HI 和去抖流程决定。只对活跃告警按测点、级别及规则身份合并，避免新因素覆盖已闭环历史。

设备类型/规则管理仅管理员可写，已登录用户可读。维修闭环增加现场诊断是否相符、现场发现和采取措施字段，保留现有备注并兼容旧客户端。数据质量记录设备上报质量码和服务器收报时间，仪表盘/测点区分在线、过期、无数据、质量异常、停机与基线学习状态；不把低振动停机判成传感器离线。

## 未实现范围留给开发者

- 具体 API 命名按项目现有 `/api/v1` 资源风格确定。
- 提供精简的通用默认类型与规则，使示范设备升级后可继续诊断。
- 阈值校验、指标/单位标签和规则配置页面要避免把阈值单位留给用户猜测。
